# sgs — 当前架构与实现设计

> 更新日期：2026-09-17。实现基线：`31af3e9`。
> 项目名称：**sgs**。
> 本文描述当前实现及边界，不再把早期计划或历史测试数字当作当前状态。
> 开发历程与大功能里程碑见 [开发里程碑总结](开发里程碑总结.md)。

## 一、项目目标与完成范围

以 Lua / LÖVE2D 实现可完整游玩的三国杀身份局，包含可独立测试的规则引擎、规则 BOT、LLM 玩家、图形牌桌、社区扩展兼容子集和单房间联机链路。游戏主体为 Lua；启动、静态检查及本地 AI 代理等工具另有 Shell、Batch、Python 实现，并非整个项目只有 Lua。

| 阶段 | 当前交付范围 | 状态与边界 |
| --- | --- | --- |
| A0 | 协程房间、杀/闪/桃最小对局、最小 UI、无头测试 | 已完成基础闭环 |
| A1 | 回合与事件管线、身份胜负、卡牌与装备、60 将名册、规则 BOT | 主体已实现；不等于 60 将所有原版模式技能均完整可用 |
| B | `sgs.*` 兼容层、技能/卡牌工厂、DIY 加载 | 约定子集已实现；仍有简化 API 和空实现，不承诺任意扩展即插即用 |
| C | 选将、完整单机牌桌、说明弹层、布局、皮肤、音频与动效 | 主体已实现；持续进行实机体验验收 |
| D | 单房间服务端、TCP 客户端、联机牌桌、观战、聊天、重连基础机制 | 核心链路已通；多房间大厅未实现，完整重连链路仍有边界 |
| E | 标准版对标：108 张固定牌堆、25 将基准、武器/救援/交互 | 标准版主要对标内容已落地；不代表所有扩展规则无差异 |
| F | LLM 全请求决策、跨步骤记忆、身份推测、思考档位、联机 AI | 主体已实现；候选集、模型协议与外部服务能力有边界 |
| 配套 | 跨平台启动、本地 AI 配置、高清缩放、回归和资源清单 | 已有实现；各平台真实环境仍需分别验收 |

阶段按历史命名保留，但实际并行推进，不能理解成严格串行的版本顺序。

### 数量口径

- 武将名册 60 名，蜀/魏/吴/群各 15；其中标准版对标集 25 名，其余为扩展名册。
- 邹氏名册保留，但国战专属能力不纳入身份局实现；不得写成“60 将全部技能无差异完成”。
- 默认 `standard` 牌堆 **108 张、32 种牌名**，花色点数固定，只随机洗序。
- `cards.lua` 内建注册表 **45 个定义：基本 8、锦囊 16、装备 21**。此数包含技能用途及兼容定义，不是标准牌堆里的卡种数；加载 DIY 后还可能增加。
- 六匹标准马使用具体名称登记，同时保留两个通用马定义供兼容使用；标准牌堆不用通用马名。
- 存在 `extended` 混堆预设，不与默认标准版的固定花色点数保证混为一谈。

## 二、架构分层与数据流

```text
main.lua / conf.lua                   启动、模式选择、窗口、无头入口
├─ src/ui/                            菜单、单机/联机牌桌、布局与资源
│  ├─ scene_room.lua                  本地 Room + Driver + 表现队列
│  ├─ scene_net.lua                   客户端快照/请求驱动的联机界面
│  └─ ai_transport.lua                love.thread 后台模型请求
├─ src/core/                          无 LÖVE 依赖的规则与决策接口
│  ├─ engine/card/cards/player        注册表、卡牌定义、角色状态
│  ├─ room/skill                      协程房间、事件和技能管线
│  ├─ standard/deck_spec              武将池、选将、牌堆与随机源
│  ├─ driver/bot                      响应调度、规则 BOT
│  └─ ai/                             观察、候选、记忆、模型决策
├─ src/net/                           Host、协议、通道、服务端与客户端
├─ src/compat/                        sgs.* API 适配与 DIY 加载
├─ diy/                               扩展示例
├─ assets/                            图片、声音、字体、皮肤配置
├─ tests/                             核心、UI、AI、网络与压测
└─ tools/                             启动、代理、自检、静态/资源校验
```

### 2.1 规则与响应源分离

`Room` 持有权威游戏状态。每个房间用一个协程执行规则：

1. `Room:start()` 创建协程并推进到等待点。
2. `askFor*` 通过 `coroutine.yield` 交出请求。
3. `Driver:advance()` 根据座位控制模式分配给人类、BOT 或 AI。
4. 人类等待 UI/网络响应；BOT 同步给结果；AI 返回 `thinking` 或结果。
5. `Room:step(response)` 恢复协程，继续按规则结算。

UI 与 AI 候选应复用 `canUseCardOn`、距离、攻击范围、出杀上限等核心查询，不能各写一套合法性规则。规则 BOT 和 LLM AI 是并列响应源，不是同一种能力的两个名称。

### 2.2 单机表现等待边界

核心发出 `useCard / respond / equip / skill / skillTarget / damage / death` 事件。单机牌桌通过监听器把事件加入表现队列。

- 单机前端登记 `room.presentationEvents` 后，在已登记事件的房间协程内产生 `type="presentation"` 等待点。
- 该请求没有 `player`，不是玩家响应请求。Driver 返回 `presenting`，不能交给 BOT/AI。
- 前端逐条播放横幅、飞牌与语音；语音忙时不继续推进规则，也不接受出牌响应。最后一条事件出队但语音仍播放时同样等待。
- 前端确认后恢复协程，最多推进到下一个等待点。缺声音时安全降级，不因素材缺失锁死对局。
- 核心只实现可选的协程边界，不读取声音或帧时钟；普通 headless 和服务端默认不登记此开关。
- 因而这是**单机表现与逻辑协调机制**，不能宣称服务端会等待每个网络客户端的音频播放完成。

## 三、规则引擎与标准身份局

### 3.1 角色、回合与胜负

| 子系统 | 实现入口 | 设计说明 |
| --- | --- | --- |
| 武将与卡牌注册 | `engine.lua`、`cards.lua` | 将可配置定义与对局实例分离 |
| 玩家状态 | `player.lua` | 体力、手牌、装备、判定区、身份、技能及标记 |
| 回合阶段 | `room.lua` | RoundStart/Start/Judge/Draw/Play/Discard/Finish；通常称六阶段回合，加回合起始事件 |
| 触发管线 | `room.lua`、`skill.lua` | 按优先级调用技能，技能可截断当前事件结算 |
| 身份与胜负 | `setupRoles`、`_checkIdentityWinner` | 主公/忠臣/反贼/内奸，隐藏身份、阵亡与终局身份公开 |
| 击杀奖惩 | `_rewardAndPunish` | 击败反贼摸牌，主公误杀忠臣承担弃牌惩罚 |
| 濒死与救援 | `_dying*` | 自救、其他角色救援、主公相关技能、死亡结算 |
| 通用原语 | `room.lua` | 摸弃牌、收牌、伤害、回复、判定、改判、翻面、拼点、跳阶段 |

单机身份局入口支持 4/5/8 人，默认 5 人，推荐 8 人；另有 2 人死斗入口。底层身份配置表支持的数量不等于菜单提供的模式。主公体力上限加成按人数规则处理，不能笼统写“所有局主公都 +1”。

### 3.2 牌堆、卡牌和装备

`deck_spec.lua` 为标准 108 张牌逐张规定牌名、花色与点数，并提供数量自检；`standard.lua` 负责实例化与确定性洗牌。测试保证每种花色 27 张和关键牌位。

- 基本牌的结算与武器、防具、伤害管线有较强耦合，入口仍在 `room.lua`；`cards.lua` 集中登记元数据、锦囊效果和装备属性。
- 延时锦囊放入判定区；同名不能重复，按后放入先判定处理；闪电未命中可继续传递。
- 四个装备槽：武器、防具、进攻马、防御马。武器影响攻击范围，马影响距离，不能混淆两者。
- 距离使用存活座位关系和攻防修正，最低 1；装备转化消耗后的距离也应按当前真实装备重新校验。
- 六匹马：绝影、爪黄飞电、的卢属于防御马；大宛、赤兔、紫骍属于进攻马。具体牌名与槽位职责分离。
- 标准对标覆盖濒死救援、主公技、无懈应答、装备效果、判定及关键技能交互；证据详见 `AUDIT-标准版对标.md` 与测试。

### 3.3 武将与技能体系

| 势力 | 名册 |
| --- | --- |
| 蜀（15） | 刘备、关羽、张飞、诸葛亮、赵云、马超、黄月英、黄忠、魏延、庞统、卧龙、刘禅、孟获、祝融、甘夫人 |
| 魏（15） | 曹操、司马懿、夏侯惇、张辽、许褚、郭嘉、甄姬、夏侯渊、张郃、徐晃、曹仁、典韦、荀彧、曹丕、乐进 |
| 吴（15） | 孙权、甘宁、吕蒙、黄盖、周瑜、大乔、陆逊、孙尚香、孙坚、小乔、太史慈、周泰、鲁肃、二张、丁奉 |
| 群（15） | 华佗、吕布、貂蝉、袁绍、颜良文丑、贾诩、庞德、张角、蔡文姬、马腾、孔融、纪灵、田丰、潘凤、邹氏 |

技能采用触发技、转化技、标记技等表达方式。非锁定技能按条件征询，内部子技能与锁定能力不当作普通主动选择。转化牌支持所需的手牌/装备区域；虚拟牌必须与实体卡牌的去向严格区分。

FilterSkill 通过 `Room:effSuit` 等统一花色入口影响判定及技能检查，已经不是只影响天香的早期实现。距离、手牌上限、攻击范围、额外目标、禁止目标等标记能力已接到核心查询。

**范围限制：**不实现国战双将、武将明暗置和阵法；邹氏保留无技能占位。名士、随势等含原版国战条件的能力有身份局近似适配，不能称为原模式的完全复现。

## 四、选将、牌桌与表现系统

### 4.1 单机完整流程

菜单选择人数/控制方式/是否选将 → 分配身份和候选 → 主公 5 选 1、其余 3 选 1 → 初始化对局 → 请求响应与行动展示 → 胜负判定和全员身份公开 → 返回菜单。

候选池去重，使用种子保证可复现；示例扩展和白板占位不进入正常随机池。关闭选将则直接随机分将。

### 4.2 交互能力

- 点选和拖拽出牌，合法目标反馈、距离/次数限制提示。
- 技能发动征询、弃牌多选、拆顺装备/判定牌、选牌和目标选择。
- 观星采用有限候选按钮，不是任意拖拽重排界面。
- 点击武将查看技能；点击装备/判定小牌查看卡牌说明。
- 身份可见性、当前回合、手牌数、装备、判定区、日志和行动提示常驻展示。
- 单机暂停/恢复和退出确认；AI 座位可动态切换控制模式。

### 4.3 布局与高清缩放

`layout.lua` 计算顺时针座位锚点，接收实际面板尺寸；`scale.lua` 根据窗口大小计算缩放因子，重新构造对应字号而非仅拉伸整个画面。

当前基准角色面板为 210×124。头像右侧放判定信息、体力和手牌数；装备在下方两列两行，名称完整显示，马带距离后缀。绘制与点击共用矩形，不能分别维护坐标。手牌区按数量自适应收拢；窗口调整、全屏和高清显示纳入布局流程。

AI 小面板与详情弹层按真实字体宽度处理文本，中文边界保持合法；长内容可通过详情弹层滚动查看。说明弹层、牌桌信息和日志属于不同绘制层级。

### 4.4 资源和音频

- `skin.lua` 解析皮肤配置及资源路径；卡牌图片使用明确名称映射，武将头像按 key 查找。
- `audio.lua` 实际加载和播放 LÖVE 音源；`effects.lua` 绘制飞牌、箭头、伤害数字、横幅和面板高亮。
- 卡牌人物配音、技能和阵亡台词参与语音等待；音频播放失败不能阻塞规则。
- 图片、字体和音频随 `assets/` 提供，也可通过 `SGS_ASSET_ROOT` 指向其他资源根。
- 缺图退回自绘，缺声音静默；皮肤数据不负责规则判定。
- 单机与联机使用不同场景实现，不能把单机全部视觉能力直接视为联机等价交付。

## 五、社区扩展兼容层

实际目录是 `src/compat/`，不是早期规划的 `src/sgs/`。

| 模块 | 能力 |
| --- | --- |
| `sgs.lua` | 常量、Package/General、技能与卡牌工厂、QVariant、原版结构体和名称归一 |
| `api.lua` | Room/Player/Card 的 API 适配、常见询问和属性接口 |
| `exppattern.lua` | 花色、点数、牌型及区域表达式匹配 |
| `loader.lua` | 发现并加载 `diy/*.lua`，注册包和武将，隔离单个脚本加载错误 |

已支持的主要构件包括 ViewAs、Trigger、SkillCard、Filter、Distance/MaxCards/AttackRange/TargetMod/Prohibit 类能力，以及常见卡牌包工厂。技能牌有独立 `_useSkillCard` 结算入口。`Card_Parse`、子卡和常见原版构造体用于降低迁移成本。

### 5.1 不变的适配原则

1. 别名经 `define()` 安装，不无意覆盖已有核心方法。
2. 未支持 API 不做万能 `__index` 静默兜底。
3. 事件常量复用核心事件；普通函数与方法的调用约定保持一致。
4. 卡片转移先摘除原区域再放入目标，避免重复登记。
5. `sgs.ai_*` 只作为兼容容器保留，规则 BOT 和 LLM AI 都不消费原版策略表。

### 5.2 已知有限语义

- 不实现国战及 `CreateArraySummonSkill`；宝物工厂映射到防具槽，没有独立宝物槽。
- 部分询问只做简化选择：如 AG 取首项、Yiji 简化分配、Exchange 退化为弃牌、兼容观星返回原序。不要与核心专用交互混淆。
- `moveCardTo` 不是完整复刻所有原版区域语义；部分区域退回弃牌堆。
- `acquireSkill` 等接口不保证完整复制原引擎的运行时技能安装语义；`changeHero`、`swapSeat` 等存在空实现。
- 部分原版表现 API 为空实现，多目标 `useCard` 和 SkillCard 候选也有简化。
- 加载示例通过只证明已覆盖子集，实际社区包需逐包核对和测试。

## 六、LLM 驱动的 AI 玩家

### 6.1 决策流水线

```text
Room 请求 → Driver → Agent
  → view 可见信息 + memory 历史
  → actions 合法候选 → prompt
  → transport 模型调用 → parse 校验
  → 记忆/身份判断更新 → 规则响应
```

| 模块 | 职责 |
| --- | --- |
| `view.lua` | 只暴露本座可知信息：自己手牌、其他人手牌数、已公开身份与场面 |
| `actions.lua` | 枚举规则允许的编号候选，将模型选择映射为核心对象 |
| `prompt.lua` | 组织状态、历史、合法候选和输出格式 |
| `parse.lua` | 解析、结构修复与编号/数量/类型校验 |
| `memory.lua` | 决策史、身份判断、长期观察、旧记录折叠 |
| `agent.lua` | 异步响应、重试、机械兜底、统计和回调 |
| `transport.lua` | mock、curl、proxy 和协议封装 |
| `src/ui/ai_transport.lua` | LÖVE worker 线程版网络请求 |
| `tools/ai_proxy.py` | 本机 HTTP 到上游 HTTPS 的代理工具 |

### 6.2 决策范围和降级

覆盖八类主要请求：出牌、响应牌、弃牌、选牌、从他人区域取弃牌、技能发动、选项、观星。AI 对这些请求默认统一走模型，而不是把响应牌自动交给规则 BOT。

模型失败时先重试并反馈错误；仍失败则按请求类型机械兜底：出牌/响应可不出，技能可不发动，强制选择取合法默认项，强制弃牌满足数量。不是所有情况都“选第一个动作”，也不能声称 `fallback="bot"` 可以恢复旧策略；当前该字段不是切换 BOT 决策的有效分支。

未知请求类型、部分 SkillCard 和观星采用有限候选。观星为原序、倒序、逐张沉底、全沉底等代表性组合，不枚举全部排列。

### 6.3 记忆和推测展示

每个 AI 座位有独立历史，模型可回传 `beliefs` 和 `note`。玩家名称/座位别名归一后保存；超预算历史折叠，避免无限增长。

菜单提供托管关/其他座位/全部，以及思考关/低/高。牌桌提供身份推测动态、判断变化时间线、理由与可用的思维摘要；这些是模型判断，不是引擎泄露的真实身份，也不是胜率保证。

### 6.4 协议、配置与异步

- **同时支持 Chat Completions 和 Responses**，可按 URL 推断或通过 `SGS_AI_PROTOCOL` 指定，不能再写“只支持 Responses”。
- 模型名由配置提供，直连需设置 `SGS_AI_MODEL`；代理模式可在代理进程配置。
- `SGS_AI_TRANSPORT=curl|proxy` 选择直连或本机代理。真实 HTTPS 请求放在 worker，UI 轮询结果。
- `SGS_AI_REASONING` 和 `SGS_AI_THINKING` 控制对应协议的推理参数；不同服务兼容程度不同，关/低/高不保证相同语义和延迟。
- `ai.env` 是本地配置，已被 Git 忽略；使用 `ai.env.example` 作为模板。Windows 和 Shell 游戏启动入口已接入读取。
- 密钥不放入文档或提交；直连用临时请求文件而非在命令行拼完整请求头。Windows 与 POSIX 权限机制不同，不能泛称全部平台均为 600 权限。
- 代理模式只有在密钥仅配置给代理进程时，才能保证游戏进程不持有该密钥。
- 不把某次模型延迟实测推广为固定性能指标；上下文增长、请求频率和服务可用性仍影响体验。

## 七、单房间联机设计

### 7.1 权威状态与协议

`Host` 持有权威 Room、座位和请求同步；客户端不能自行裁决规则。`protocol.lua` 使用一行一个 JSON；卡牌和玩家对象被转换为可传输的数据，再由 Host 在应答时还原。

| 模块 | 职责 |
| --- | --- |
| `channel.lua` | 内存通道用于确定性测试，TCP 通道用于实际连接 |
| `host.lua` | 占座、准备、开局、请求编号、应答、状态/日志广播、聊天和座位恢复 |
| `server.lua` | LuaSocket 监听、连接消息分流、主循环和服务端 AI |
| `client.lua` | welcome/state/req 等消息接收与响应发送 |
| `scene_net.lua` | 图形客户端牌桌和请求交互 |

已形成连接 → 占座 → 准备 → 开局 → 请求/应答 → 胜负广播链路。默认至少两名真人准备后开局，其余位置由规则 BOT 或指定 LLM 填充。服务端可在一局后继续接受下一局。

### 7.2 观战、聊天、重连与服务端 AI

- 观战不占玩家席位，接收公开状态/日志并可聊天；聊天保留有限历史。
- Host 提供断线座位保留（默认 60 秒）与令牌恢复接口，Client 提供 resume 消息。
- 对局中新连接会先进入观战路径；当前该路径未完整处理 resume。因此“存在重连 API/测试”不等于“局中真实 TCP 自动重连已完整可用”。
- 客户端不是自动重连器，公开快照也未包含全部装备/判定信息；联机界面不与单机牌桌完全等价。
- `SGS_NET_AI=1/on/all` 或座位列表可把空座交给 LLM；默认关闭时走 BOT，人类入席优先。
- 服务端在 LÖVE 环境下优先使用线程传输；同步降级不应被描述为无条件非阻塞。
- 多房间大厅、统一账户系统不属于当前已完成链路；网络边界与跨机器稳定性需单独验收。

## 十、开发约定与维护边界

1. **BOT ≠ AI**：前者是规则脚本，后者是 LLM 响应源；`sgs.ai_*` 是原版兼容表名。
2. **核心不依赖 LÖVE**，表现与传输通过接口接入；请求对象不保证一定含 `player`。
3. 修改 Lua 后执行 `run-tests.sh`；规则与调度变化另跑网络和压测。新测试先验证前提，不能把“没有执行到”当通过。
4. `Cards.define` 集中登记卡牌属性、名称、类型和说明；普通锦囊效果优先放在定义中。基本牌现有结算仍由 Room 负责，新增能力避免继续散落重复规则。
5. 调用技能工厂前核对点号/冒号约定，`TriggerSkill.create` 为点号形式；普通回调也不可自动当方法调用。
6. 技能拥有者与事件主体分开校验：如 `data.from`、`data.to`、`data.player`；`can_trigger` 应排除无关事件，避免无意义征询。
7. 会 `askFor*` 的测试放入协程；涉及表现的测试要覆盖队列、语音状态和实际规则推进，而非只看队列长度。
8. 转化技出牌能力需同步检查 BOT 候选与 AI 枚举；用同一套核心合法性查询。
9. 阵营判断不能只比较身份文本；主公与忠臣身份不同但同阵营。
10. phantom 虚拟牌不能被实体收牌/弃牌逻辑重复登记；卡牌移动必须保持守恒。
11. 规则以本地标准版资料和参考实现核对，不凭记忆补技能；明确身份局适配与原版模式差异。
12. UI 使用同一缩放、测量与命中矩形；长中文按完整 UTF-8 字符和真实字宽处理。
13. 配置密钥不入库，运行时二进制和本地工具产物按忽略规则处理，不读取密钥填文档。
14. 本项目 Git 作者与提交者使用 `catsonkeyboard <leemeany@gmail.com>`；提交只包含本次明确改动。
15. 文档变更同步更新“实现状态”和“边界”，历史性能、数量或计划不得继续冒充当前事实。
