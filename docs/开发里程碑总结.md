## 一、总体结论

项目已从“杀、闪、桃能跑完的小型原型”，发展为包含标准身份局规则、武将技能体系、完整单机牌桌、LLM 玩家、扩展适配和单房间联机能力的可玩项目。

可以将当前版本描述为：**单机主体功能基本完成，AI 决策和可视化已接入，单房间联网链路已形成，进入体验验收与边界完善阶段。**

不宜描述为“完整商业联机产品”或“原版全部模式、全部扩展完全复刻”。名册规模、兼容 API 存在、测试全绿和完整产品验收是不同概念。

## 三、各大里程碑的实现说明

### M1：从原型到可扩展的规则内核

**目标**：首先证明游戏能从初始化走到结束，而不是只做一个可点击的界面。

**实现方式**：
- 将武将/卡牌注册、玩家状态、规则房间、技能事件分别建模。
- 用 Lua 协程表达“结算执行到这里，需要某个玩家作出响应”，避免把规则散落在 UI 回调中。
- 以 `Room:step` 和 `Driver` 作为规则与响应源之间的边界，人类操作和自动对手均通过请求/响应参与。
- 从杀、闪、桃的迷你局扩展到触发管线、阶段机、判定和牌堆。
- 从起步阶段就建立无窗口测试，核心不依赖图形系统。

**成果价值**：后续身份局、BOT、LLM 玩家和网络服务端都复用同一套规则模型，而不是分别实现多个游戏引擎。

**主要模块**：`src/core/engine.lua`、`card.lua`、`player.lua`、`room.lua`、`driver.lua`、`skill.lua`。

### M2：建立完整标准身份局与固定牌堆

**目标**：由简单对战升级为具有角色阵营、隐藏信息和完整结算的身份局。

**实现方式**：
- 建立主公、忠臣、反贼、内奸的分配、可见性、阵营胜负及击杀奖惩。
- 将判定、摸牌、出牌、弃牌等阶段与伤害、濒死、救援、死亡接成完整流程。
- 引入基本牌、即时锦囊、延时锦囊、武器、防具和攻防马的规则表达。
- 对照标准版资料，收敛到 108 张固定花色点数的默认牌堆，并以数据表和测试约束数量。
- 将标准武将、主公技、装备效果、无懈响应和救援等纳入对标与交互完善。
- 支持常用 4/5/8 人身份局入口，默认 5 人、推荐 8 人，并保留 2 人死斗入口。

**成果价值**：标准模式的内容和流程有明确数据基准，牌堆不再只是随机比例生成的近似集合。

**当前边界**：默认标准牌堆为 108 张、32 种牌名；扩展混堆与内建定义总数是不同口径，不能把“45 个定义”当成“标准版 45 种牌”。

**主要模块**：`src/core/deck_spec.lua`、`standard.lua`、`cards.lua`、`room.lua`；标准版审计与对标测试。

### M3：形成武将技能库与规则 BOT

**目标**：让对局具有不同武将的能力差异，并在无外部服务时仍能完整进行。

**实现方式**：
- 按蜀、魏、吴、群建设各 15 名武将的名册。
- 用触发技、转化技、标记技等通用机制表达武将能力；补充改判、拼点、翻面、阶段跳过等引擎原语。
- 将距离、范围、手牌上限、额外目标与禁止目标等能力统一接入规则查询。
- 建立规则 BOT，通过同一响应协议处理出牌和应答，并识别常见转化技和阵营关系。
- 采用多种子和逐将覆盖的对局测试验证长期运行与卡牌守恒。

**成果价值**：扩展武将可以复用机制组合，不必为每名角色重新搭建交互循环；本地 BOT 提供无需联网的可玩基础和测试对手。

**当前边界**：60 是名册数量，不是全部原版技能无差异完成的承诺。邹氏的国战专属能力未实现；部分国战来源能力采用身份局适配。BOT 是脚本决策，不能称为具有模型推理能力的 AI。

**主要模块**：`src/core/generals.lua`、`skill.lua`、`bot.lua`、`room.lua`、`player.lua`。

### M4：建设社区扩展兼容和 DIY 加载能力

**目标**：保留利用既有 `sgs.*` 风格扩展定义的可能性，降低新增内容的接入成本。

**实现方式**：
- 建立 `sgs` 命名空间、常量、Package/General 和常见结构体。
- 适配触发技、转化技、技能牌、过滤技、标记类技能及卡牌包工厂。
- 提供常见 Room/Player/Card 方法别名和询问接口。
- 通过 ExpPattern 解析花色、点数、牌型及区域条件。
- 在加载器中扫描 DIY 脚本，注册内容，并隔离单个脚本的加载失败。
- 示例包用于验证兼容能力，但不进入正常随机选将池。

**成果价值**：内容扩展不再局限于修改核心注册文件；原版风格的脚本构件可以在已支持范围内复用。

**当前边界**：这是有限语义适配，不是原版引擎的完整替代。部分询问简化、表现接口为空、宝物映射防具槽；不实现国战，也不执行原版 `sgs.ai_*` 策略表。实际包仍需逐个验收。

**主要模块**：`src/compat/sgs.lua`、`api.lua`、`exppattern.lua`、`loader.lua`、`diy/`。

### M5：打通从菜单、选将到终局的单机操作闭环

**目标**：从“规则能自动跑”升级为“真人能够理解、选择并完成一局”。

**实现方式**：
- 菜单提供局型、人数、选将和 AI 控制选项。
- 实现主公 5 选 1、其他座位 3 选 1，候选去重，选将后建立对局。
- 支持点选和拖拽出牌，显示合法目标及距离等反馈。
- 将技能发动、目标选择、弃牌多选、装备/判定区选择等规则请求映射为可操作 UI。
- 提供武将技能和卡牌说明入口，集中呈现对局状态。
- 支持单机暂停、恢复和退出，胜负结束后公开身份并返回菜单。

**成果价值**：人类玩家不再只是观看 BOT 对局，能够参与关键选择，形成完整交互闭环。

**当前边界**：部分复杂交互采用候选按钮而非任意操作界面，例如观星没有全排列拖拽重排；联机客户端也不是单机 UI 的完整镜像。

**主要模块**：`src/ui/scene_menu.lua`、`scene_room.lua`、`skill_desc.lua`、`src/core/standard.lua`。

### M6：建立资源化、可读且按节奏展示的牌桌

**目标**：将文字原型升级为带角色识别、规则反馈和行动节奏的可视化牌桌。

**实现方式**：
- 接入皮肤配置、卡牌插画、武将头像、勾玉、势力标识和桌面背景。
- 自带资源并通过统一路径和名称映射查询，缺失时回退到自绘或静默。
- 用事件驱动飞牌、指向箭头、伤害数字、技能横幅、面板高亮和声音。
- 将音频与图形展示解耦：没有台词仍能显示技能反馈。
- 单机通过表现队列和可选协程事件边界，将语音播放与后续规则推进协调起来。
- 统一窗口/DPI 缩放、字体尺寸、座位锚点和点击矩形，支持窗口调整及全屏。
- 对手牌数量、装备/判定区域和长文本提供适应性布局。

**成果价值**：玩家可以识别是谁对谁做了什么；画面和行动推进不再只是同步逻辑的瞬间输出。后续的视觉收尾均属于这个里程碑，而不是新的玩法系统。

**当前边界**：真实声音听感、不同分辨率及平台窗口效果需实机确认；服务端不等待各客户端音源结束。

**主要模块**：`src/ui/skin.lua`、`layout.lua`、`scale.lua`、`audio.lua`、`effects.lua`、`text_fit.lua`。

### M7：形成单房间多人联机基础

**目标**：让不同客户端通过共享权威规则房间进行同一局游戏。

**实现方式**：
- 建立 Host、座位、准备、开局、请求编号及应答验证。
- 以通道抽象隔离规则同步与 socket，提供内存通道测试和真实 TCP 通道。
- 使用逐行 JSON 传输可序列化请求、公开状态和日志。
- 打通控制台及图形客户端，让玩家能够接收请求并提交响应。
- 添加观战、聊天、座位保留和令牌恢复基础机制，服务端可继续承接下一局。
- 接入服务端 AI，让空座可由 BOT 或指定 LLM 填充。

**成果价值**：项目不再只有本地单机驱动，规则可由独立权威服务端复用。

**当前边界**：没有多房间大厅；Host 的令牌重连能力不等于真实局中自动重连完整闭环。当前新连接进入观战分支后，resume 消息的衔接仍不完整；联机公开快照也未覆盖全部单机牌桌信息。应记为“单房间核心已实现，联网体验仍有待完善范围”，而非“联机全功能完成”。

**主要模块**：`src/net/protocol.lua`、`channel.lua`、`host.lua`、`server.lua`、`client.lua`、`src/ui/scene_net.lua`。

### M8：引入真正由 LLM 决策的 AI 玩家

**目标**：让外部模型承担玩家决策，而不是仅给规则 BOT 添加文字解释。

**实现方式**：
- 在 Driver 中增加与人类/BOT 并列的 AI 响应源。
- 观察层限制可见信息，合法动作层枚举编号候选，模型选择经解析校验后转换为核心响应。
- 覆盖出牌、响应牌、弃牌、选牌、拆牌、技能发动、选项和观星八类主要请求。
- 模型请求在 LÖVE worker 中执行，主线程轮询 `thinking/ready`，保持界面可响应。
- 支持 Chat Completions、Responses，及 HTTPS 直连/本机代理两条传输路径。
- 解析失败可反馈重试，持续失败采用按请求类型定义的机械兜底，不默认回退为规则 BOT。

**成果价值**：AI 的决策来源与规则 BOT 明确分离；模型可以替任意指定座位作决策，又不能绕过核心规则任意创造动作。

**当前边界**：候选集不是无限策略空间，部分 SkillCard 和复杂重排有简化；协议兼容不等于所有服务都兼容。模型不可用时维持对局不挂起，但不保证兜底具有正常策略质量。

**主要模块**：`src/core/ai/view.lua`、`actions.lua`、`prompt.lua`、`parse.lua`、`agent.lua`、`transport.lua`、`src/ui/ai_transport.lua`。

### M9：让 AI 具有连续记忆并展示身份推理过程

**目标**：支持身份局需要的跨回合判断，让用户能够观察 AI 的认知变化。

**实现方式**：
- 为每个 AI 座位维护决策记录、身份判断和长期观察。
- 将历史与当前可见状态共同送入提示词，而不是每步孤立调用。
- 归一玩家别名，记录身份判断变化，对过长历史做预算控制和折叠。
- 菜单提供思考强度选择，牌桌呈现推测动态和可滚动的详情时间线。
- 通过回调展示理由和可用的思维摘要，不把真实隐藏身份直接提供给模型。

**成果价值**：AI 从“单步出牌器”发展为可以积累对局信息的玩家；其判断过程具有可观察性，方便调试和对比不同模型。

**当前边界**：推测是模型输出而非真实身份裁定，思考档位的实际效果和延迟取决于服务；没有统一胜率或推理正确率保证。

**主要模块**：`src/core/ai/memory.lua`、`agent.lua`、`prompt.lua` 和牌桌 AI 展示部分。

### M10：完善本地交付、跨平台入口和质量保障

**目标**：让项目不只在开发者单一进程中可用，还能配置、运行、验证和继续维护。

**实现方式**：
- 资源独立放入 `assets/`，游戏运行不再依赖旁边的参考源码目录。
- 提供 Shell/Windows 启动工具、便携运行时查找/准备、本地 `ai.env` 配置及示例。
- 为模型接入提供代理、自检和演示脚本，避免将真实密钥写入源码。
- 建立核心、UI、AI、网络五类测试维度以及批量压测。
- 在测试入口加入方法调用静态检查、素材文件清单校验。
- 区分代码和素材许可，明确分发所需检查；文档记录运行环境与适用范围。

**成果价值**：后续开发可以在稳定的测试和交付基础上迭代，而不是每次依赖手工试打一局判断是否可用。

**当前边界**：运行时二进制不随 Git 追踪；跨平台脚本存在不等于所有目标系统已逐台验收。测试通过也不自动形成商用授权或可发布的平台产品。

## 四、功能如何组合成一局游戏

### 本地对局

```text
菜单配置 → 分配身份/选将 → Room 初始化
  → Driver 按座位选择 人类 / BOT / LLM AI
  → 核心验证响应与规则结算
  → 事件进入单机表现队列并协调语音等待
  → 更新可见牌桌和 AI 记忆
  → 下一请求/下一回合 → 胜负与身份公开
```

### 联机对局

```text
客户端连接/准备 → Host 建立权威 Room
  → 请求按座位发往客户端或服务端 BOT/AI
  → 应答还原并交给规则核心
  → 广播公开状态/日志 → 客户端展示
```

两种模式共享规则，但不应假定展示能力、重连完整性和声音同步完全相同。

## 五、当前完成度与明确边界

### 已形成主体交付的范围

1. 可从开局走到终局的单机标准身份局。
2. 以 108 张标准牌堆和武将能力为基础的规则系统。
3. 真人交互、规则 BOT、LLM AI 三种响应来源。
4. 选将、资源化牌桌、音效动效和 AI 推测展示。
5. 单房间服务端和客户端请求/应答链路。
6. 社区扩展有限兼容和持续回归测试基础。
